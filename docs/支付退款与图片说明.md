# 业务与图片存储说明

## 库存口径

`product.stock` 表示**可售库存**。创建待支付订单时立即扣减，作为该订单预留，不在付款成功时重复扣减。创建订单事务包含按商品ID排序锁定商品、再次验证上架/删除标记、原子条件更新库存、保存订单与明细快照和库存日志。失败时全部回滚，避免超卖或半张订单。

未付款取消和30分钟超时取消均恢复预留库存。`stock_restored`保证仅恢复一次。商家手工调整的是可售部分，不能扣减到负值，也无法动用已被订单预留的部分。

## 支付

`POST /api/payment/mock/{orderId}` 是明确命名的**模拟支付接口**，由后端校验登录用户、订单归属和待支付状态，支付金额只读取订单数据库快照。客户端不提交金额或直接修改支付状态。

模拟失败为 `POST /api/payment/mock/{orderId}/fail`；保持待支付。成功保存独立payment_record（订单唯一约束）、模拟交易号和时间，订单进入待接单。重复成功请求返回已有订单结果，不重复创建流水。

创建订单必须传 `request_key`。同用户重复同键返回首次订单；前端在一次结算中复用同一键。换一次新结算才生成新键。

## 退款

`refund_status`：1待审核、2处理中、3成功、4拒绝、5失败。申请必须是自己的已支付且尚有可退金额的有效订单。后台锁定订单，校验金额大于0且最多两位小数，不超过支付额减去累计成功退款；待审核/处理中/失败退款均视为未解决，禁止并行新申请。

商家同意后进入2，定时任务每5秒调用事务处理。只在模拟渠道处理成功后写成功状态、累计退款与退款流水。重复调用只对状态2生效，避免重复退款。失败会保留原因，商家可以重试；`MOCK_REFUND_FAIL=true`仅用于测试渠道失败，关闭后可重试。

部分退款不会自动取消整个订单或恢复整束花库存。累计全额退款取消订单；待接单或已接单尚未制作的订单恢复库存，制作/配送/完成后的退款不自动恢复花材，避免将已消耗花材重新变为可售。

商家拒单只允许待接单且无未解决退款的已支付订单。订单记录拒绝原因，同时自动创建剩余全额的退款处理中记录，不能只改状态。商家拒单退款失败只能重试，不能再次拒绝该退款。

制作后退款申请可提交供商家根据实际履约情况审核，本系统不自动判定现实法律义务。

## 账单统计

支付成功额仅统计payment_record中状态1；成功退款额仅统计refund_record中状态3。

`模拟净收款 = 模拟支付成功金额 - 模拟退款成功金额`。

待支付、审核中、退款处理中或退款失败金额不混入成功统计。账单范围汇总分别按支付时间/退款时间纳入，适合核对期间净流入；账单单笔记录显示该订单累计成功退款与单笔净收款。人气排行按已支付订单明细的数量/金额排序，属于付款商品毛额排行，不是扣除退款后的净销量。

## 图片文件

`UPLOAD_DIR`控制根目录，默认 `./data/uploads`，正式部署示例 `D:/flower-upload` 或 `/var/lib/flower-mall/uploads`。相对路径相对于backend工作目录。

```text
UPLOAD_DIR/
  products/detail/    商品上传文件（封面与详情共用安全文件池）
  reviews/images/    用户实拍评价图片
  avatars/           用户头像
```

封面通过 `product.cover` 与 `product_image.image_type=cover` 关联，详情为独立product_image；评价图片存review_image，不将多张图片拼接进评价正文。路径 `/uploads/...` 由Spring静态映射提供，MySQL只保存URL、归属和用途等元数据。

上传格式支持真实JPG、PNG和WEBP，扩展名/MIME不是唯一判断依据。服务端使用ImageIO与WEBP解码插件验证内容，限制原图3000万像素、单文件5MB、每业务最多9张详情/评价图。上传时读取图片尺寸再解码，缩放至最长边不超过2000，去掉元数据并重新编码成JPEG（透明区域填白），使用UUID文件名。

商品封面只能使用本地演示图或当前商家上传的product用途图片；评价/头像只能引用自己且用途一致的上传记录。原始文件名不作为存储路径，上传目录不执行脚本。前端展示与预览不使用HTML解释图片内容。

事务回滚时清理本次上传文件；删除文件前检查商品封面/详情、订单快照、评价及头像引用。任何引用存在则保留；闲置图片可在商家图片管理中删除。商品逻辑删除仍保留图片引用；删除用户评价也保留可审计的原记录引用。数据库和磁盘的删除跨介质不能构成同一原子事务，删除物理文件失败会记录服务日志，需运维清理闲置文件。

## 与SRS的实施取舍

- 用户与管理员存储在统一account表，通过role、独立登录接口/令牌存储和后台权限拦截隔离；不将两套密码放在前端。
- 本地演示额外提供H2持久化配置，MySQL8是正式部署配置且已实际测试。
- 商品封面与详情使用统一的products/detail物理文件池，避免同图设主图时移动文件导致历史URL失效；逻辑封面/详情仍独立标记。
- 图片当前为插画演示数据，上传后由本地服务器提供实拍图。无外部AI密钥时为显式模板模式。
- 登录用户可在商品评价区填写依据举报，商家评价管理中可见举报记录；审核评价会标记已处理并保留依据日志。内容审核为人工流程。
