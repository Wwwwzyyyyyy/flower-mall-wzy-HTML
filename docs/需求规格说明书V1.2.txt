第一章 项目概述

1.1 项目背景

随着互联网电商和人工智能技术的发展，传统花店逐渐向线上化、数字化经营转型。传统花店主要依靠线下门店销售，存在商品展示范围有限、订单处理效率低、库存管理不方便、客户维护困难等问题。

本项目计划开发一套集鲜花在线销售、花语文化展示、AI祝福语生成、商品图片管理、用户真实图片评价、订单管理、库存管理、退款审核和经营数据统计于一体的AI智能花店电商管理系统。

系统分为用户端和商家管理端。

用户可以在线浏览鲜花商品、查看商品实物图片、了解花语、购买花束、使用AI生成祝福语、管理订单、申请退款以及上传真实商品评价图片。

商家可以管理商品、上传商品图片、调整库存、处理订单、审核退款、查看用户评价以及统计经营数据。

通过引入人工智能和图片展示功能，提高鲜花商城的个性化服务能力和商品展示效果。

1.2 项目建设目标

实现鲜花商品线上展示与销售。

实现用户注册、登录、购物车、订单及个人中心管理。

建立鲜花花语图鉴，展示不同花卉及其文化寓意。

接入AI API，实现个性化祝福语生成。

实现商家商品新增、修改、删除及上下架管理。

实现商家上传商品封面图片和详情图片。

实现花束库存查询、增加、减少和手动调整。

实现用户购买鲜花、订单处理和配送管理。

实现用户退款申请及商家退款审核。

实现用户对购买商品进行文字评价、星级评分和真实图片上传。

实现商家查看用户评价及评价图片。

实现用户信息管理和消费数据统计。

实现商家营业额、订单量及经营情况汇总。

实现模拟支付和模拟退款，保证第一版核心业务流程完整。

2.2 系统架构

系统采用前后端分离架构。

前端通过 Axios 向后端发送 HTTP 请求，后端使用 Spring Boot 接收请求，调用 Service 业务层处理业务逻辑，通过 MyBatis 操作 MySQL 数据库。

AI祝福语功能由后端调用第三方AI API。

图片上传功能由前端选择图片，通过 MultipartFile 上传至后端，后端校验文件并保存到服务器本地目录，MySQL保存图片访问地址。

支付功能由后端模拟支付，不接入真实支付渠道。

2.3 系统分层

表现层：Vue 3 用户端和商家端。

接口层：Spring Boot Controller。

业务层：Service。

数据访问层：Mapper。

数据层：MySQL 8.0。

文件存储层：服务器本地图片目录。

外部服务层：第三方AI API。

第五章 图片存储与管理需求

5.1 存储方式

第一版采用服务器本地文件夹存储，不使用云对象存储。

图片文件保存在后端服务器指定目录，MySQL仅保存图片元数据和访问地址。

5.2 本地目录结构

D:/flower-upload/
├── products/
│   ├── cover/
│   └── detail/
├── reviews/
│   └── images/
└── avatars/

目录说明：

products/cover：商品封面图片。

products/detail：商品详情图片。

reviews/images：用户评价图片。

avatars：用户头像。

5.3 图片访问地址

数据库保存相对访问地址，例如：

/uploads/products/cover/abc123.webp
/uploads/products/detail/def456.jpg
/uploads/reviews/images/ghi789.jpg
/uploads/avatars/avatar001.png

后端通过静态资源映射提供图片访问。

5.4 图片上传规则

支持JPG、JPEG、PNG、WEBP格式。

单张图片大小不超过5MB。

商品封面图片每个商品只能有一个有效封面。

商品详情图片最多9张。

用户评价图片最多9张。

图片上传前进行预览。

后端再次验证文件大小和实际文件格式。

文件名使用随机唯一名称。

不允许上传可执行脚本。

上传失败时返回明确错误信息。

删除图片时同步处理文件和数据库记录。

订单商品图片需要保存历史快照，避免商品图片更新影响历史订单。

5.5 图片存储安全

图片上传目录不能允许执行脚本。

图片文件名不能由用户直接指定。

需要校验文件真实内容，不能只检查扩展名。

限制上传文件大小。

用户只能删除自己有权限管理的图片。

管理员只能管理具有对应权限的商品图片。

正式部署时需要定期备份本地图片目录。

第九章 系统非功能需求

9.1 性能要求

常规业务接口在正常网络及合理负载下，目标响应时间不超过2秒。

AI接口单独设置超时时间。

商品、订单、用户及评价列表需要分页查询。

高频查询字段建立合理索引。

订单和库存操作保证事务一致性。

图片文件应采用适当压缩和尺寸控制，避免影响页面加载。

9.2 安全要求

用户密码必须进行安全哈希处理。

使用JWT进行身份认证。

用户端和商家端实行权限隔离。

用户只能访问自己的订单、地址、退款及评价记录。

商家接口必须进行管理员身份校验。

AI API Key不得暴露在前端。

后端必须验证关键业务参数。

防止重复提交订单和重复退款。

防止越权访问及SQL注入。

正式部署时使用HTTPS。

图片上传需要校验文件实际格式、大小及内容。

上传文件不得作为可执行脚本运行。

9.3 数据安全要求

订单数据必须持久化保存。

商品信息变更不能影响历史订单快照。

商品图片应保留必要的历史订单图片引用。

库存变动必须保存操作记录。

退款操作必须保留审核记录。

评价及评价图片必须关联真实用户和订单商品。

重要业务操作必须具备异常回滚能力。

对用户个人信息进行必要保护。

本地图片目录应定期备份。

数据库应定期备份。

9.4 兼容性要求

用户端适配常见电脑及移动浏览器。

商家后台优先适配桌面浏览器。

页面具有良好的可读性和操作体验。

图片展示应适配不同屏幕尺寸。

第十五章 需求确认与设计约束

前端固定采用Vue 3 + Vite + JavaScript，不使用TypeScript。

后端采用Java 17 + Spring Boot + MyBatis。

数据库采用MySQL 8.0。

系统采用前后端分离架构。

用户端和商家端使用不同的权限体系。

商品图片和用户评价图片必须使用独立图片记录表。

图片文件存储在服务器本地目录，MySQL只保存图片元数据及访问地址。

图片存储目录通过配置文件管理，不能将图片路径写死在代码中。

第一版采用模拟支付，不接入真实微信支付。

第一版采用模拟退款，不产生真实资金交易。

商品上下架状态与库存数量分开管理。

订单必须保存商品及收货信息快照。

用户评价必须关联已购买商品及订单明细。

库存调整、订单扣减及退款处理必须保证数据一致性。

AI API Key必须保存在后端。

用户不能通过修改前端参数绕过订单、支付、退款和库存校验。
